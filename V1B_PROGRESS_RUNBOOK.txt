Design in use: **design 1 — VPS hosts the API and the UDP pair-forwarder relay.**
The routed two-interface hub in VPS_RELAY.txt §3 (design 2) is intentionally
NOT used: it is unnecessary and would need VPS routing/default-route changes.

needs NO VPS routing, NAT, FORWARD or default-route changes.

================================================================================
2. ARCHITECTURE (design 1)
================================================================================
        Remote phone ── HTTPS (control) ──┐
                       UDP relay pair ────┤
                                          ▼
                            ODIVORA VPS  204.13.234.26
                            ├─ odivora-api   127.0.0.1:8000   (control plane)
                            └─ odivora-relay 127.0.0.1:9090 (control, loopback)
                                             UDP 20000-20999 (pair forwarding)
                                             UDP 3478 (rendezvous, optional)
                                          ▲
                       outbound HTTPS + UDP from home
                                          │
        Home Ubuntu gateway (behind Starlink CGNAT) ── wg0 + NAT ── Starlink ── Internet

WireGuard path: phone <-> gateway (both peers), endpoints are the relay's
per-session UDP ports. The relay copies ciphertext only. No port forwarding at
home; no static home IP; no router changes.

13. PHASE E/F — PHONE + REAL ROUTE + REVOCATION
================================================================================
Phone Wi-Fi OFF, on mobile data (Safaricom/Airtel/other). Same account that
claimed the gateway.

1. POST /api/v1/connections {"gateway_id": ...}                  -> session id
2. POST /api/v1/sessions/{id}/authorize-wg {}                    -> assigned_ip + relay
3. GET  /api/v1/sessions/{id}/wg-config                          -> odivora-xxxx.conf
4. Import into WireGuard app, bring tunnel up.
5. POST /api/v1/sessions/{id}/handshake                          -> status connected
6. On the phone: open an HTTPS page and check the public IP equals the HOME
   Starlink egress IP (same as any device on the home Wi-Fi).
7. Disconnect: POST /api/v1/sessions/{id}/revoke-wg -> peer must vanish from
   `sudo wg show` on the gateway within one sync interval, phone returns to LTE.
8. Revocation: revoke gateway/device -> no new session/peer can re-establish.

Record REAL measurements (latency/packet loss/throughput). Do not invent them.
Verify the VPS default route, SSH, website and API still work throughout.
Keep traffic low-volume; the VPS has limited RAM.

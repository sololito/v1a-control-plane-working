# ODIVORA Home Connectivity — Complete V1B Integration and Remote Connectivity Test

You are the lead networking engineer and backend developer for the ODIVORA Home Connectivity project.

Your task is to complete our V1B data-plane integration, connecting the existing ODIVORA application to a Linux home gateway behind Starlink CGNAT, with a remote phone connecting over mobile data.

We have already demonstrated that our application can generate a WireGuard configuration and establish a VPN when both devices are on the same network. The ESP32 has also successfully registered and completed pairing with the backend.

Now we must prove that a remote phone can use the home's internet connection **without port forwarding, a static home public IP, or changes to the TP-Link/Tenda or Starlink router**.

The existing VPS hosts production ODIVORA services. I will personally run all critical commands on that VPS.

- Running commands that could interrupt SSH access or change the VPS's default route.

You may inspect and modify the **project source code in the designated development repository**, run local tests and prepare scripts and configuration templates.

For every required VPS or home-gateway operation:

## 3. Target test architecture

We will use the existing VPS temporarily as a routed WireGuard hub, with two WireGuard interfaces.

```text
                     ODIVORA VPS
                  Public IP 204.13.234.26
                            |
            +---------------+---------------+
            |                               |
       wg-phone                         wg-home
       UDP 51820                        UDP 51821
       10.200.1.1                      10.200.2.1
            |                               |
            |                               |
        Remote phone                   Home Ubuntu
        10.200.1.2                     10.200.2.2
        Mobile data                    Starlink LAN
                                            |
                                      Home router
                                            |
                                         Starlink
                                            |
                                         Internet
```

The intended end-to-end IPv4 traffic path is:

```text
Remote phone
    |
    | WireGuard tunnel A
    v
VPS: wg-phone
    |
    | Linux forwarding and source-based policy routing
    v
VPS: wg-home
    |
    | WireGuard tunnel B
    v
Home Ubuntu gateway
    |
    | IP forwarding and NAT
    v
Home router
    |
    v
Starlink
    |
    v
Public Internet
```

Return traffic must travel back through the home gateway and VPS to the phone.

The home gateway must initiate an outbound WireGuard connection to `relay.odivora.com:51821`. The phone connects to `relay.odivora.com:51820`.

Use `PersistentKeepalive = 25` where appropriate for the NATed peers.

The home router should need no port forwarding, static IP, DDNS, or VPN configuration.

### Important encryption limitation

For this initial test, the two WireGuard tunnels terminate independently on the VPS. The VPS therefore decrypts packets from one tunnel before forwarding and encrypting them into the other.

This is a temporary laboratory hub design, **not end-to-end encryption between the phone and home gateway**. Do not describe it as opaque relaying or as production-ready end-to-end encryption.

Document this limitation clearly. A future direct peer-to-peer path or encrypted-packet relay is a separate architectural phase.

## 9. Phase Six — integrate the existing control plane

After the basic network configuration has been validated, connect it to the existing ODIVORA control plane.

Use the existing APIs and session contracts discovered during the audit.

The desired lifecycle is:

```text
Phone authenticates
        |
        v
User/device authorization
        |
        v
Request own gateway connection
        |
        v
Check gateway, ownership/grant and entitlements
        |
        v
Create authorized session
        |
        v
Provision the authorized WireGuard peer
        |
        v
Home gateway syncs its authorized peer configuration
        |
        v
WireGuard handshake
        |
        v
Verify actual connectivity
```

The system must not accept a user-supplied `gateway_id` without checking authorization server-side.

When a session is ended, expired or revoked, its phone peer must be removed or disabled promptly.

When a device or gateway is revoked, a stale configuration must not allow continued access indefinitely.

The implementation should distinguish clearly between:

- `AUTHORIZED`: the control plane approved the connection.
- `TUNNEL_ESTABLISHED`: the WireGuard peer has a recent valid handshake.
- `INTERNET_VERIFIED`: real traffic has successfully exited through the home connection.

Do not report a session as successfully connected to the internet merely because an API returned HTTP 200.

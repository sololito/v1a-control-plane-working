# Objective of V1B

Build the first working **WireGuard data plane**.

The goal is to prove this real scenario:

```text
             HOME

TP-Link/Tenda Router
        │
        │ Ethernet
        ▼
Linux/OpenWrt Gateway
        │
        │ WireGuard
        │
        ▼
   ODIVORA Cloud
   (coordination only)
        ▲
        │
        │ WireGuard
        │
    Mobile Client
    outside home
```

The final desired traffic path is:

```text
Phone
  │
  │ encrypted WireGuard tunnel
  ▼
Home Gateway
  │
  ▼
Home Router
  │
  ▼
Home ISP
  │
  ▼
Internet
```

**Normal user internet traffic MUST NOT pass through the ODIVORA application/API server.**

The ODIVORA cloud remains primarily:

* identity
* authentication
* authorization
* gateway registry
* session coordination
* configuration/signalling
* audit/usage metadata

A relay may be introduced later as a fallback, but it is NOT part of the first direct-path implementation.

---

# Important architecture decision

For this phase, **DO NOT use the ESP32 as the primary WireGuard/data-plane gateway**.

Use a normal Linux machine or OpenWrt-capable device as the first real gateway.

The development gateway should be capable of:

* WireGuard
* IP forwarding
* NAT
* firewalling
* routing
* DNS handling

The ESP32 remains part of the existing control-plane experimentation and may later be integrated into the final hardware architecture.

The first objective is to prove the networking architecture on capable Linux/OpenWrt hardware before optimizing for embedded hardware such as MT7981.

---

# 1. Preserve V1A

Before changing anything:

* inspect the existing repository
* understand the current architecture
* run the complete existing test suite
* confirm V1A remains green
* do NOT rewrite working authentication/pairing logic unnecessarily

Create a clear separation between:

```text
CONTROL PLANE
and
DATA PLANE
```

Do not merge networking traffic into the existing REST API.

---

# 2. Choose WireGuard

Use **WireGuard** as the tunnel technology.

Do not implement a custom VPN protocol.

Use standard WireGuard tooling/kernel support available on Linux/OpenWrt.

The project should manage WireGuard configuration programmatically where appropriate.

The eventual architecture should support:

```text
PHONE/WIREGUARD PEER
        ↕
HOME GATEWAY/WIREGUARD PEER
```

The ODIVORA backend coordinates the relationship but does not proxy normal data traffic.

---

# 3. Gateway abstraction

Create a gateway data-plane abstraction so we can later support:

* Linux gateway
* OpenWrt gateway
* MT7981-based ODIVORA Home Key
* potentially other gateway hardware

Do not hard-code the networking layer to one Linux command or one hardware platform.

Conceptually:

```text
Gateway
 ├── identity
 ├── control-plane connection
 ├── tunnel capability
 ├── WireGuard public key
 ├── tunnel address
 ├── data-plane status
 └── software/firmware version
```

---

# 4. WireGuard identity

Each gateway should have a WireGuard keypair.

Private keys MUST:

* never be sent to the cloud
* never be stored in plaintext in backend logs
* never be exposed through normal API responses
* remain local to the gateway

The cloud may store the gateway's:

* public key
* tunnel IP/address assignment
* metadata
* peer state

The mobile client should also generate/manage its own WireGuard identity securely.

---

# 5. Session authorization

Use the existing V1A connection authorization mechanism.

The flow should become:

```text
Phone
  │
  │ request connection
  ▼
ODIVORA Cloud
  │
  ├── authenticate user
  ├── authenticate device
  ├── verify gateway ownership/grant
  ├── verify gateway online
  ├── verify subscription/entitlement
  ├── verify session limits
  │
  ▼
Create authorized session
  │
  ▼
Issue short-lived tunnel/session configuration
```

Do not let the mobile client independently decide whether it is allowed to access a gateway.

The backend remains the authority.

---

# 6. Dynamic WireGuard peer configuration

Implement the minimum mechanism required to authorize a phone as a WireGuard peer for its selected gateway.

The exact implementation may use:

* backend-generated peer configuration
* short-lived session credentials
* gateway synchronization
* configuration polling
* WebSocket signalling
* another secure mechanism

Choose the cleanest architecture.

Do not expose private gateway keys.

Do not create permanent peers for every user if temporary session peers are more appropriate.

Consider:

* peer expiration
* session termination
* revocation
* reconnect
* device revocation
* gateway revocation

---

# 7. Tunnel IP addressing

Design a private tunnel address scheme.

For example:

```text
10.x.x.x/...
```

or another appropriate private range.

The system must prevent:

* address collisions
* two users receiving the same active tunnel address
* one user accessing another user's gateway without authorization

Do not hard-code one IP for all users.

Create an allocation abstraction that can later scale to many gateways/users.

---

# 8. Gateway routing

Configure the Linux/OpenWrt gateway so traffic coming from the WireGuard interface can reach the home LAN and/or internet through the existing home router.

The desired path is:

```text
WireGuard interface
       ↓
Gateway routing
       ↓
Home LAN / WAN interface
       ↓
Existing router
       ↓
Home ISP
```

The customer's existing TP-Link/Tenda router should NOT need:

* WireGuard configuration
* port forwarding
* DDNS
* special VPN setup

For the initial prototype, the gateway simply connects to the existing router using Ethernet/DHCP.

---

# 9. Internet egress / NAT

Configure the gateway so that remote tunnel traffic can be NATed toward the existing home router when required.

The final behavior should be:

```text
Remote phone
   ↓
WireGuard
   ↓
ODIVORA Gateway
   ↓
NAT
   ↓
Home Router
   ↓
Home ISP
```

The home router should see the gateway as a normal LAN device.

Do not require changes to the customer's existing router for this phase.

---

# 10. Split tunnel vs full tunnel

Implement configuration support for both concepts, but prioritize **full-tunnel internet access** for the first demonstration.

Full tunnel:

```text
Phone
  ↓
WireGuard
  ↓
Home Gateway
  ↓
Home Internet
```

The mobile client's internet traffic should exit through the home ISP.

Later we can support:

* LAN-only access
* split tunnel
* configurable routes

But the first success criterion is full internet egress through home.

---

# 11. DNS

Handle DNS deliberately.

Avoid accidentally leaking DNS outside the tunnel when full-tunnel mode is enabled.

The first implementation may use:

* home DNS
* a configured DNS resolver
* a secure resolver reachable through the tunnel

Document the choice.

The mobile client should be able to verify whether DNS requests are following the intended path.

---

# 12. NAT / CGNAT

The first data-plane implementation should NOT assume that the home gateway has a public IP.

The home gateway should establish its control-plane connection outbound.

For the first data-plane experiment, use the simplest reliable WireGuard coordination strategy possible.

Do NOT build a relay yet unless necessary for the basic test.

However, design the interfaces so that a future connection path can be:

```text
DIRECT
or
RELAY
```

without rewriting the session model.

---

# 13. Relay architecture — future-ready only

Do not build full relay infrastructure in this phase.

Create only the abstraction/documentation necessary for:

```text
Phone ←──── DIRECT ────→ Gateway
```

and later:

```text
Phone ←── Relay ──→ Gateway
```

The relay must eventually carry encrypted WireGuard traffic without becoming the termination point for user traffic.

For now, mark relay functionality as TODO.

# 19. Security requirements

Treat WireGuard configuration and credentials as sensitive.

Do NOT:

* send private keys to the backend
* log private keys
* expose private keys through debugging APIs
* create unauthenticated gateway peers
* allow arbitrary user-selected gateways
* trust client-supplied ownership
* bypass existing authorization
* disable TLS
* disable authentication for convenience

Use short-lived session authorization where practical.

Ensure disconnect/revocation removes or invalidates the relevant peer.

# Definition of DONE

V1B is complete only when we can demonstrate this with real equipment:

```text
                HOME

       TP-Link/Tenda Router
                │
             Ethernet
                │
                ▼
         Linux/OpenWrt
            Gateway
                │
                │ WireGuard
                │
                ▼

            INTERNET

                ▲
                │
                │ WireGuard
                │
                ▼

       Phone outside home
       on mobile data/
       different Wi-Fi
```

The phone must:

1. Authenticate to ODIVORA.
2. Request its own authorized gateway.
3. Receive authorized tunnel configuration.
4. Establish a real WireGuard tunnel.
5. Route internet traffic through the home gateway.
6. Reach the public internet.
7. Show the home's public IP as the egress IP.
8. Disconnect cleanly.
9. Lose access when the session/device/gateway is revoked.

Do not move to commercial billing or marketplace features until this end-to-end data-plane test is working reliably.

## Guiding principle

**V1A proved identity and authorization. V1B must prove actual connectivity.**

Use proven WireGuard and Linux/OpenWrt networking components. Do not invent a custom VPN protocol or custom cryptography.
